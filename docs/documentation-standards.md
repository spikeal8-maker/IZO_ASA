# Стандарт читаемых документов IZO_ASA

Порядок чтения — только `AI_START_HERE.md`; текущая работа — `docs/NOW.md`.
Формат задания и scope — существующий Task Contract. Этот документ задаёт
размер и структуру рукописных материалов, а не вторую очередь разработки.

## Размеры и назначение

| Вид | Цель | Максимум |
|---|---|---|
| Навигатор / README | 40–80 строк | 120 строк и 8 КиБ UTF-8 |
| Тематический Markdown | 80–150 строк | 200 строк и 12 КиБ UTF-8 |
| NOW | Краткий статус | Собственный контракт: 140 строк и 8 КиБ |
| Предметная карта | Одна область | Действующий контракт `docs/context/`: 100–250 строк |
| Сгенерированный материал | Проверяемый вывод | Только генератор; не обрезать вручную |
| Архив | Историческое свидетельство | Не читать автоматически как текущее требование |

Строки — физические строки файла; байты — размер UTF-8. Оба предела проверяются.
Кодовые 500/750 строк определяет `architecture/contract.json`, не этот документ.
Тесты и фикстуры: [testing-file-standards.md](testing-file-standards.md).

## Как разделять

Один смысловой контракт — один файл; большая тема получает короткий индекс
с прямыми ссылками на главы. Сначала сохранить требования/примеры/таблицы,
проверить полноту и ссылки, затем отдельно менять содержание. Не удалять
существенные правила или регрессионные проверки ради формального лимита.

Прежний нормативный оригинал при структурном разбиении сохранить в архиве
с тем же Git blob. Архив и Git-история не становятся действующими заданиями.
Пример: [Design System 2.0](IZO_ACA_Design_System_2.0-full.md).

## Автоматический контроль

`tools/file_hygiene.py` проверяет размеры изменённых файлов и новые ошибки
локальных ссылок между Git-деревьями. Для PR используется общая база ветвления,
для push — явный диапазон изменений; отчёт содержит запрошенный и фактический base.

Проверяются Markdown/HTML-ссылки, ссылки через идентификаторы, разделы Markdown,
явные пути в обратных кавычках, корневые и эксплуатационные документы.
Перенос файла требует перепроверки относительных целей. Архив → рабочий каталог
означает новый активный документ, а не разрешение вернуть прежний монолит.
Ссылки из блоков примеров не исполняются. Внешние HTTP-адреса не обходятся.

Старые превышения и прежние битые ссылки учитываются отдельно как долг.
Изменённый старый сверхлимитный документ не может расти ни в строках, ни в байтах.
Важную инструкцию при необходимости сначала разделить без потери смысла.
Автоматических исключений для Markdown сейчас нет: изменение политики требует
отдельного согласованного решения, а не комментария, обходящего проверку.

Parser — hash-pinned MarkdownIt из `tools/file_hygiene_requirements.txt`,
только для CI/tools, не зависимость контейнера приложения. Расширения footnote
и якоря в файлах вне Markdown/HTML не проверяются; полного semantic audit это не заменяет.

## Приёмка

Основной CI вызывает reusable `.github/workflows/file-hygiene.yml` на Linux.
Документальные/явно перечисленные portable-изменения не запускают Windows job;
неизвестные, прикладные и изменяющие его шаги пути сохраняют полную проверку.
Ошибка лёгкого gate не превращается в PASS последующим шагом pipeline.

Перед объединением нужны результаты точного SHA и независимая проверка согласно
`AGENTS.md`. Собственный комментарий исполнителя не является review или разрешением
пропустить CI. Наличие workflow не доказывает его успешный запуск или готовность Docker.
