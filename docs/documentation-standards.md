# Стандарт читаемых документов IZO_ASA

**Дата решения:** 2026-10-17. **Область:** рукописная документация. Этот стандарт не является второй очередью задач и не меняет порядок чтения из `AI_START_HERE.md`. Условия конкретной задачи и допустимые файлы определяет её Task Contract.

## 1. Ограничения размера

| Вид | Цель | Верхняя граница |
|---|---|---|
| Навигатор большого документа | 40–80 строк | 120 строк и 8 КиБ UTF-8 |
| Новый тематический Markdown | 80–150 строк | 200 строк и 12 КиБ UTF-8 |
| `docs/context/*.md` | Короткая карта владения | Действующее правило 100–250 строк; отдельный existing contract |
| Сгенерированные файлы | Детерминированный вывод | Изменять только генератор, не обрезать вручную |
| Исторические отчёты `archive/**` | Сохранённые свидетельства | Не считать рабочими документами и не загружать автоматически |
| Задания `tasks/*.toml` | Границы одного пакета | Формат и лимиты определяет Agent Control Plane |

**Строка** — физическая строка файла; **размер** — байты UTF-8, а не число букв. Оба условия обязательны для новых рукописных тематических документов. Для уже существующих больших документов превышение является **долгом на безопасное рассредоточение**, но не основанием ломать текущие runbook-операции или блокировать необходимое исправление критического контракта.

Для **исходного кода** действует существующая `architecture/contract.json` / `source_size_policy` и `docs/generated/architecture-inventory.md` (обычный максимум 500 строк, пересмотр после 750; большие защищённые файлы имеют собственные бюджеты). Не добавлять параллельные лимиты кодовой базы в Markdown.

## 2. Одна тема — один владелец

1. Найти текущий канонический документ, а не создавать его двойник.
2. Крупный файл заменить коротким **указателем с названием разделов** и прямыми относительными ссылками.
3. Делить по смысловым заголовкам/контрактам: UI, API, data, security и operations не смешивать.
4. Длинный оригинал сохранить в `archive/` в том же commit **без изменения исходного Git blob**. Архив не является источником новых заданий.
5. У каждого нового файла должны быть понятное имя, локальная структура, контекст применения и ссылка через указатель. Повторять правила `AGENTS.md` / `NOW.md` нельзя.
6. При изменении маршрутов обновлять имеющиеся ссылки. Глубокие anchors на старую монолитную страницу требуют проверки; отсутствие таких проверок записывать в PR.
7. Сначала доказать эквивалентность/сохранность текста, затем — при необходимости — отдельным пакетом исправлять само содержание. Не смешивать структурное разбиение с изменением продукта или UI.

## 3. Что проверять при каждом структурном изменении

- Текущий `main` и конфликтующие ветки; один writer на затронутые пути.
- Каждая глава документа присутствует ровно один раз, ни один раздел/пример/таблица не потерян и не обрезан.
- Максимальные строки/байты, корректность всех локальных ссылок, отсутствие дубля владельца статуса или правил.
- Старые файлы/источники доступны по конкретному SHA для восстановления.
- `docs/context/` и `docs/generated/` не подменяют своим содержимым авторский документ и не редактируются вручную.
- Targeted checks, Package scope, review и требуемые CI receipts фиксируются раздельно. Статические проверки документа не равны успешному Docker/production и не заменяют CI, когда он обязателен.

## 4. Как поступать с исключениями

Не повышать лимит ради прохождения проверки. Если неделимая таблица/кодовый пример вынуждает превысить порог, зафиксировать точную причину в отдельном Task Contract, указать файл/владельца, минимальное необходимое отклонение и план последующей декомпозиции. Для действующих runbooks по восстановлению, безопасности и платежам смысл и полнота важнее формальной экономии строк.

Первый пример структурного разбиения: [Design System 2.0](IZO_ACA_Design_System_2.0-full.md), где 31 нумерованный раздел размещён в 10 тематических файлах; индекс открывается один раз, затем — только нужная глава.

## 5. Автоматическая проверка в GitHub

`tools/file_hygiene.py` проверяет **только изменённые** рукописные Markdown и тестовые файлы по точному `base SHA → head SHA`. Новые документы должны укладываться в приведённые выше пределы; существующие сверхлимитные файлы допускаются только без роста строк и байтов. Новый Markdown-link должен разрешаться в checkout; удаление ссылочного файла не должно оставлять сломанную активную ссылку. Архив и generator-owned документы не обрезаются ради размеров. Контекстные карты сохраняют собственные 100–250 строк.

Это отдельная лёгкая проверка GitHub-hosted Linux без Docker, npm и настоящих сервисов. Она **не заменяет** профильные, runtime или Docker tests. Для тестовых файлов и их лимитов см. [стандарт тестов](testing-file-standards.md).
