# Provider route preflight — изолированный контракт

Статус: bounded implementation только для offline preflight;
не подключён к runtime, не создаёт денежных обязательств.
Исходный Task: `PROVIDER-ROUTE-PREFLIGHT-001`.
Связанные будущие этапы: GitHub issues #203 (registry), #204 (durable failover).

## 1. Для чего предназначен модуль

`backend/app/services/provider_route_preflight.py` формирует отчёт
о пригодности **кандидатов** из доверенного backend registry.
Входные кандидаты уже упорядочены администратором. Проверка не меняет
этот порядок и не вызывает Ollama, ComfyUI, OpenRouter или DeepSeek.

Применение только после server-side загрузки и валидации:
идентификации, прав пользователя, каталога моделей, тарифов,
health, цен и серверного бюджета. Ни одно из этих полей
не должно приниматься от браузера как утверждение о допуске.

## 2. Результат

`PreflightReport.evaluations` — упорядоченные записи с причиной
`ELIGIBLE` либо конкретного отказа.
`candidates_for_further_admission` — **не разрешение отправки**,
а короткий список для следующей транзакционной стадии.

Никаких запросов, платежей, сохранения состояния и смены провайдера
этот модуль сам не производит. Он не является действующим маршрутизатором или диспетчером.

## 3. Доверенные серверные снимки

- `ProviderState` сообщает ID, тип, строго `enabled=True`,
  health=`ready`, время проверки, проверенные модели и операции.
- `ModelCapability` требует `verified=True` и точную operation.
  Наличие модели в общем каталоге не разрешает её использование.
- `AccessContext` содержит server-side `authorized_routes`,
  явное разрешение платной операции и конечный доступный бюджет.
- `PriceQuote` содержит только проверенную сервером цену
  в `Decimal`, operation, время и признак проверенного источника.
- `RouteChoice` — запрошенные provider/model в порядке приоритета.
  Повтор одной пары provider/model отклоняется.

Вход должен быть сформирован на backend после доверенной проверки.
Этот контракт сознательно не поддерживает хранение/шифрование ключей.

## 4. Ограниченные возможности

| Provider kind | Операции в первоначальном контракте |
|---|---|
| Ollama | chat |
| DeepSeek-direct | chat |
| OpenRouter | chat, text_to_image, image_edit, text_to_video, image_to_video, asr, tts |
| ComfyUI | text_to_image, image_edit, text_to_video, image_to_video |

Строка означает лишь верхнюю границу возможного для типа.
Конкретная модель обязана иметь отдельно проверенную capability.
Ни одна модель не наследует всё перечисленное автоматически.

## 5. Fail-closed условия

- Запрещены неизвестные операции и provider kinds.
- Невозможно использовать отключённого или неготового провайдера.
- Health устаревает через 300 секунд; будущие и timezone-naive
  временные метки отклоняются.
- Модель отсутствует, дублируется, не проверена либо несовместима —
  кандидат отклонён.
- Требуется точное server-side право на provider/model/operation.
- Облачная модель не считается бесплатной только по полю `free`.
- Платная модель требует явного `paid_allowed`, подтверждённой
  положительной конечной котировки не старше 300 секунд
  и достаточного бюджета.
- Нулевая, отрицательная, NaN/Infinity, неподтверждённая,
  просроченная или дублирующаяся котировка не подходит.
- Кандидатов не более 16; повторная пара не допускается.

## 6. Чего этот контракт не гарантирует

Он не проверяет подлинность утверждений исходного backend registry:
эту ответственность несёт будущий серверный loader.
Не предотвращает TOCTOU после health/price check.
Не делает резервирование токенов, определение provider receipt,
двойную отправку или окончательное settlement.
Не гарантирует endpoint isolation и защиту от SSRF.
Не реализует cooldown, retry, выбор после неизвестного результата.
Не предоставляет API или UI, не подключён к продукту.

Перед каждым фактическим SEND обязателен **повторный authoritative
preflight внутри транзакции** вместе с durable command identity,
quoting/reservation, атомарной проверкой доступа и состоянием операции.
`ACCEPTED`/`OUTCOME_UNKNOWN` нельзя передавать другому провайдеру
до reconciliation. Это отдельный следующий Task из issue #204.

## 7. Проверки и внедрение

- Offline unit-тесты: `backend/test_provider_route_preflight.py`.
- Статус реальных внешних вызовов: NOT_RUN.
- Docker backend/user runtime: NOT_RUN.
- Host live Ollama: отдельные ранее выполненные read-only проверки;
  не считается доказательством этого preflight.
- Main и Shadow этим кодом не изменяются.
- CI и независимый review остаются обязательными для последующего
  слияния и фактического включения dispatcher.
