# Независимая установка и проверка Docker

Пакет объединяет существующие PR #186 и #191 относительно main
`d1ee3a0ac5114ec08f4a8daee9cf6e41e97d6a7a`. Их исходные коммиты остаются
предками интеграционной ветки. Это инструкция кандидата; наличие файлов
не подтверждает прохождение приёмки. Критерии: `docs/docker-delivery-acceptance.md`.

## Исполнитель и запуск

Workflow `.github/workflows/docker-clean-install.yml` запускается при push
в `agent/docker-clean-install-001` и вручную. Он использует временные
GitHub-hosted Ubuntu 24.04 VM с правами `contents: read` и точным checkout SHA.
Проверка Task Contract и секретов выполняется перед сборкой приложения.
Общий Windows-исполнитель этим workflow не запускается.

Две matrix-задачи получают разные VM. Каждая заново собирает три образа,
последовательно, из одного чистого checkout; затем выполняет три прогона
на новых собственных SQLite/media volumes. Внутри одной VM второй и третий
прогоны повторно используют уже проверенные immutable image IDs.
Вторая VM заново строит образы и повторяет сценарии независимо.

Драйвер `python -m tools.docker_clean_install` требует точные `--source-sha`,
`--base-sha`, номер `--replica 1|2` и новый каталог `--evidence-dir` внутри
`RUNNER_TEMP`. Он отказывается работать на общем или неподтверждённом host.
Docker context `default`, локальный Unix socket, engine ID и хеш machine ID
фиксируются и проверяются при действиях. Настройки Docker и сети хоста
не изменяются. При занятом порте запуск заканчивается ошибкой.

## Что выполняется

| Критерий | Исполняемое доказательство |
|---|---|
| Д1-01 | Чистый exact checkout, source/config hash, локальные image IDs и размеры |
| Д1-02 | Настоящая готовность API, изолированная сеть, Chromium и SHA веб-страницы |
| Д1-03 | Два пользователя через регистрацию API; вход, выход, неверный пароль, чужие объекты |
| Д1-04 | UI/API → очередь → обработчик → ComfyUI HTTP fixture → файл → галерея → учёт |
| Д1-05 | Сохранённая галерея, избранное и повторное использование изображения |
| Д1-06 | Разрешённая публикация, гостевая лента, pending moderation и приватность |
| Д1-07 | Пересоздание с теми же volumes; сессии, баланс, журнал, медиа и публикации |
| Д1-08 | Desktop/mobile screenshots, ограниченные редактированные журналы, собственная очистка |

Проверка провайдера доступна только с явным `compose.acceptance.yml`.
Он живёт в сетевом пространстве backend и слушает loopback. Эфемерный
control token остаётся в памяти; наружу выдаётся только безопасная квитанция.
Время жизни ограничено 300 секундами. `COMFYUI_MOCK_FALLBACK=false` исключает
успех за счёт внутреннего обходного генератора. Обычный backend CMD сохранён.

Фикстура заменяет только модель. Авторизация, очередь, файлы, SQLite,
галерея, публикации и финансовый учёт принадлежат приложению. Браузер
не подменяет API; дополнительные внешние запросы браузера блокируются.
Доступ к приватному изображению проверяется отдельным гостевым контекстом.

Используется документированный стабильный ключ режима `APP_ENV=test`.
Это позволяет проверить сохранность сессий в изолированной CPU-фикстуре;
поставка и резервирование production-секрета этим тестом не подтверждаются.

## Доказательства и сбои

`clean-source-…` содержит source gates, regression logs и результаты pytest.
Каждый `clean-linux-…` содержит `summary.json`, отдельные `run-N/receipt.json`,
`topology.json`, квитанции провайдера, сравнение SQLite/media, снимки чужих
ресурсов до/после, изображения экранов и `containers.redacted.log`.
Artifact name включает source SHA, workflow run ID и attempt; срок — 14 дней.
Ссылки на фактические runs и ограничения добавляются в PR после исполнения.

Неуспешный прогон не повторяется скрыто. Следующий push/attempt получает
отдельный набор артефактов. Уже существующий каталог evidence не перезаписывается.
Пропавшая квитанция, screenshot, журнал или незавершённая очистка не дают PASS.

Очистка разрешена только после доказательства, что project был новым,
и повторной проверки labels непосредственно перед удалением. Удаляются
собственные контейнеры, сеть и volumes. Docker images/build cache остаются
в границах одноразовой VM и её штатного завершения; global prune отсутствует.
Обычная команда Shadow `down` по-прежнему сохраняет volumes.

## Границы результата

Начальная топология содержит один прикладной процесс и встроенный обработчик.
Д2 recovery, конкуренция, backup/restore и отказ хранилища требуют отдельных
исполняемых результатов; Д1 не заменяет их. CPU/RAM/диск/время в квитанциях —
измерения конкретной фикстуры, без выдуманных production-нормативов.

Живые ComfyUI/Ollama/Qwen, платные API, SMTP, Telegram/MAX, реальные платежи
и production не проверяются этим workflow. Статус таких подключений —
`NOT_VERIFIED`, пока нет отдельного разрешённого испытания. Адрес loopback
принадлежит VM исполнителя и недоступен владельцу после завершения job.
Production-переход #126 остаётся отдельным согласованным этапом.
