# OpenRouter video: каталог в админке

Дата: 2026-07-15

Статус: каталог, тарифный доступ и предварительная бухгалтерия готовы. Пользовательская видеогенерация еще не подключена.

## Что реализовано

- Backend получает модели из отдельного OpenRouter endpoint `GET /api/v1/videos/models`.
- Ответ нормализуется в `backend/app/integrations/openrouter.py`; одна битая строка не ломает весь каталог.
- Каталог кешируется на 6 часов тем же сроком, что и каталог возможностей изображений.
- `GET /api/admin/models-page` отдает `openrouter.videoCatalog`, ошибку загрузки и имя источника.
- В `Админ -> Модели -> OpenRouter` появился раскрывающийся блок `Видео OpenRouter`.
- Модели разделены на сценарии: по тексту, по изображению, по первому и последнему кадру, по референсам.
- Для каждой модели видны длительности, разрешения, пропорции, поддержка кадров, аудио, seed, параметры и опубликованные цены.
- У каждой модели и каждого режима есть отдельные флаги включения и доступа для `Mini`, `Plus`, `Pro`, `Business`.
- Видеомодели оформлены той же финансовой таблицей, что и модели изображений: общий чекбокс режима, чекбокс модели слева и общие чекбоксы тарифных столбцов.
- Настройки хранятся отдельно от изображений в `admin_settings.openrouter_video_models` и очищаются backend от неизвестных режимов, тарифов и моделей.
- Завершенные OpenRouter video jobs агрегируются отдельно в `openrouter.videoUsage`: число генераций и фактические расходы по режимам и моделям. Неполученная стоимость не превращается в искусственный ноль.

## Правила классификации

| Сценарий | Проверяемый признак |
|---|---|
| По тексту | модель присутствует в специализированном video endpoint |
| По изображению | `supported_frame_images` содержит `first_frame` |
| Первый и последний кадр | присутствуют `first_frame` и `last_frame` |
| По референсам | описание модели содержит явное упоминание reference-to-video или reference images |

Последний сценарий помечен в интерфейсе как предварительный: текущий каталог OpenRouter не отдает отдельное структурированное поле с максимальным числом референсов. Перед включением такой модели нужен контрактный живой тест.

## Цены

`pricing_skus` сохраняется без потери ключей. Значения с префиксом `cents_per_` переводятся из центов в доллары. Неподдерживаемое разрешение не показывается, даже если у провайдера в цене остался лишний SKU.

Для каждой опубликованной длительности таблица показывает себестоимость в USD и RUB, минимальное целое число проектных токенов, выручку, прибыль и фактическую маржу.

В основной строке используется единый контрольный вариант для быстрого сравнения моделей: `5 секунд + 1080p`. Если модель его не поддерживает, выбирается ближайшая к пяти секундам длительность, затем `720p`, а после нее лучшее опубликованное разрешение. Это только сравнительный пример; раскрытая матрица остается источником расчета всех поддерживаемых комбинаций.

```text
effective_usd_rub = usd_rub * 1.30
cost_rub = cost_usd * effective_usd_rub
minimum_revenue_rub = cost_rub / (1 - minimum_margin_percent / 100)
project_tokens = ceil(minimum_revenue_rub / token_price_rub)
```

При текущих настройках используются `5 ₽/токен` и минимальная маржа `40%`. Округление всегда выполняется вверх, поэтому фактическая маржа равна или выше заданной.

### Типы биллинга видео

1. Секундный: ставка SKU умножается на длительность. Разрешение и наличие аудио выбираются только из опубликованных возможностей модели.
2. Видеотокенный: используется формула `width * height * duration_seconds * 24 / 1024`, затем результат умножается на стоимость одного видеотокена.
3. Входной кадр: `cents_per_image_input` добавляется для image-to-video; для первого и последнего кадра учитываются два входа.

Для видеотокенных моделей одно название разрешения недостаточно: `720x720` и `1280x720` имеют разное число пикселей и разную себестоимость. Поэтому строки таблицы разделяются по фактическому размеру и пропорции.

Фактический `usage.cost`, полученный после завершения video job, должен стать источником окончательного списания и аудита. Таблица в админке нужна для предварительной цены и резервирования; расхождение с `usage.cost` будущий pipeline обязан компенсировать идемпотентной доплатой или возвратом.
