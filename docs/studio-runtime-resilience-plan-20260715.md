# План защиты студии от runtime-падений

Дата: 2026-07-15
Статус: P0 завершён
Область: основной интерфейс `/`, API-контракты, CI, публикация и мониторинг.

## Цель

Одна некорректная запись, один изменённый API-контракт или один сбой отдельного
виджета не должны останавливать студию целиком. Не прошедшая runtime-проверку
сборка не должна становиться публичной.

## Инцидент, который закрывает P0

`GET /api/gallery/items` начал отдавать основное изображение в `viewerSrc` и
`downloadUrl`, а студия ожидала `url`. Значение `undefined` дошло до строковой
операции и активировало корневой `ErrorBoundary`. Компиляция прошла, потому что
JSON-ответ не проверялся во время выполнения, а browser smoke не входил в CI.

## Обязательные принципы

1. Любые внешние данные считаются недоверенными до runtime-нормализации.
2. Компонент получает только проверенную внутреннюю модель.
3. Ошибка истории, галереи или подсказки не останавливает генерацию.
4. Build без browser smoke не является готовым релизом.
5. Новая сборка сначала проверяется, затем атомарно становится публичной.
6. Ошибка у пользователя автоматически попадает в журнал и вызывает оповещение.
7. Для каждой production-аварии создаётся воспроизводимый regression test.

## P0. Не допустить повторения текущего сбоя

### Действия

- Нормализовать новый, старый и частично повреждённый ответ галереи на границе API.
- Отбрасывать элементы без рабочего URL, не передавая их в React.
- Защитить строковые операции и подписи от `null`/`undefined`.
- Расширить `e2e:studio-resilience` сценариями:
  - новый контракт `viewerSrc`/`downloadUrl`;
  - старый контракт `url`;
  - отсутствующий `id`;
  - пустые и посторонние элементы;
  - отсутствие корневого аварийного экрана;
  - рабочие миниатюры и выбор результата.
- Сделать E2E самодостаточным: отдельный preview, перехваченные API-ответы,
  гарантированная остановка тестового процесса.
- Добавить `e2e:studio-resilience` в `tools/verify.ps1` для Full и CI.

### Критерий готовности

`lint`, `build`, контрактный E2E и тест плана CI проходят. Если удалить
нормализацию или снова обратиться к отсутствующему URL, CI становится красным.

## P1. Локализация ошибок интерфейса

### Действия

- Разделить большой `newUi.tsx` минимум на контейнеры HistoryDock,
  GalleryPicker, Preview и StudioForm.
- Поставить локальные ErrorBoundary вокруг HistoryDock, GalleryPicker и Preview.
- Для каждого блока сделать рабочий fallback с кнопкой повторной загрузки.
- Корневой ErrorBoundary оставить только последней защитой.
- Не показывать пользователю stack trace; показывать короткое сообщение и
  идентификатор инцидента.
- Сохранять промпт и настройки перед повторным монтированием.

### Критерий готовности

Искусственная ошибка каждого блока отключает только этот блок. Промпт,
навигация и кнопка генерации остаются доступны.

## P2. Единые runtime-контракты

### Действия

- Вынести схемы GalleryItem, FeedItem, GenerationResult, AuthSession и ModelInfo
  в отдельный frontend contract layer.
- Для каждого API иметь parser, normalizer и безопасный fallback.
- Добавить backend contract tests на публичную форму ответа.
- Запретить прямое использование `response.json()` в UI-компонентах.
- Версионировать несовместимые API-изменения или поддерживать переходный адаптер.

### Критерий готовности

Поиск по UI не находит прямой передачи непроверенного JSON в состояние React.
Старый и новый fixtures проходят один набор контрактных тестов.

## P3. Безопасная публикация и откат

### Действия

- Собирать релиз в отдельный каталог с Git SHA и manifest.
- До переключения публичного трафика запускать API smoke и browser smoke.
- Переключать активный release только после зелёных проверок.
- Хранить две последние рабочие сборки.
- Добавить одну проверяемую команду rollback.
- Запретить публикацию из грязного дерева и из папки вне канонического проекта.
- Защитить `main`: обязательный CI, запрет прямого обхода проверок.

### Критерий готовности

Намеренно сломанная сборка не меняет публичную версию. Откат к предыдущему SHA
выполняется одной командой и подтверждается smoke-проверкой.

## P4. Наблюдаемость и автоматическое оповещение

### Действия

- Отправлять frontend runtime errors с release SHA, маршрутом, режимом и
  обезличенным идентификатором сессии.
- Не отправлять промпты, cookies, токены и содержимое изображений.
- Добавить синтетическую проверку `/`, `/feed`, `/gallery`, `/profile`:
  загрузка, отсутствие ErrorBoundary, наличие ключевого элемента.
- Оповещать при первой новой сигнатуре ошибки и при превышении порога ошибок.
- Отображать release SHA и состояние синтетической проверки в админке.

### Критерий готовности

Тестовая runtime-ошибка появляется в журнале с release SHA и вызывает
оповещение, но не раскрывает пользовательские данные.

## P5. Регулярные аварийные учения

- Раз в месяц проверить повреждённый gallery item, недоступный backend,
  устаревший frontend, 401 refresh loop и неудачный release.
- Зафиксировать время обнаружения и восстановления.
- Любой найденный пробел превращать в автоматический тест.

## Release gate после завершения P0

```powershell
.\tools\verify.ps1 -Mode CI
```

Минимальная последовательность: backend tests, frontend lint, frontend build,
origin isolation, studio runtime resilience. Любой ненулевой код останавливает
публикацию.

Проверено 2026-07-15 командой `tools/verify.ps1 -Mode CI`: 1348 backend-тестов,
frontend lint, production build, origin isolation и studio runtime resilience
прошли. Lint сохранил одно ранее существовавшее предупреждение React Hooks без
ошибок.

## Порядок реализации

1. P0: контрактный E2E и обязательный CI gate.
2. P1: локальные границы ошибок и декомпозиция History/Gallery/Preview.
3. P2: общий слой схем для остальных API.
4. P3: атомарный release и rollback.
5. P4: мониторинг и синтетические проверки.
6. P5: регулярные аварийные учения.
