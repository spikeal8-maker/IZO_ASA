# ИЗО АСА — технические требования и приёмка контейнерной поставки

## 1. Назначение и граница

Этот документ задаёт испытания результата, а не новый порядок задач. Маршрут
поставки принадлежит мастер-ТЗ, активный пакет — `docs/NOW.md`, порядок чтения —
`AI_START_HERE.md`. Применять документ после слияния утверждающего его PR.

Здесь изложены **требования к будущей реализации**, а не отчёт о выполненных тестах.
Описанное испытание получает PASS только после настоящего запуска на указанной
версии. Наличие pytest-файла, ссылки на него или этой таблицы не является PASS.

## 2. Идентичность проекта и неприкосновенные ресурсы

- Единственный репозиторий: `spikeal8-maker/IZO_ASA`.
- Пользовательское имя: ИЗО АСА; пространство ресурсов Docker: `isoas`.
- Справочный рабочий домен из действующей документации: `https://izo.alikinas.ru/`.
  Здесь не подтверждается его актуальный сервер и не разрешается изменение DNS/FRP.
- Похожие `izo-asa` и `izo-asa-platform` — другие репозитории. Их код, образы,
  данные, временные каталоги и конфигурации не использовать как основу.
- `izo-asa-preview`, `asa-lab-*`, Publikator и прочие чужие проекты не изменять,
  не останавливать, не переименовывать и не включать в группу ISOAS.

На пользовательском сервере сначала получить read-only список своих/чужих ресурсов
и занятых портов. Предпочтительный локальный порт 5200 не считается свободным по
старому отчёту. При занятости выбрать свободный loopback-порт и показать фактическую
привязку; не освобождать его остановкой чужого контейнера. Ошибка bind — не повод
перезапускать Docker Desktop.

Одна установка — одна Compose-группа `isoas`; параллельные одноразовые CI-прогоны
используют уникальное `isoas-ci-<run-id>-<attempt>`. Имена внутри группы задаёт Compose.
Нельзя жёстко назначать одинаковые container_name нескольким тестовым запускам.
Общие product-labels: `io.isoas.project=ISOAS` и `io.isoas.public-url` со справочным
доменом. Окружение и идентификатор прогона записываются отдельно.

API, БД, внутренние хранилища и имитаторы не публикуются в Интернет. Временный
браузерный стенд слушает loopback; доступ владельца к нему требует отдельной
согласованной публикации. Ссылка 127.0.0.1 исполнителя CI владельцу недоступна.

## 3. Контейнеры, данные и конфигурация

### Начальная топология Д1

Веб-часть раздаёт собранные ресурсы и проксирует запросы серверу. Сервер на Д1 имеет
один прикладной процесс с прежними встроенными обработчиками, если они ещё не
отделены. Это допустимая промежуточная конфигурация, явно отмеченная в отчёте.

SQLite не требует отдельного контейнера БД. База, WAL/SHM и связанные файлы находятся
в одном постоянном локальном томе. Медиаданные — в отдельном томе. Не подключать
чужие или рабочие тома для испытаний. Не использовать сетевую файловую систему для
многопроцессного WAL без отдельно доказанной совместимости.

### Целевая топология Д2–Д4

Отдельный обработчик имеет устойчивый источник заданий, протокол захвата/аренды,
ограничение конкурентности, результат и правила восстановления. Сервер без роли
обработчика не запускает вторую копию потребителя. Несколько контейнеров не делят
внутрипроцессный Python-объект очереди.

Отдельные контейнеры для галереи, ленты, авторизации и платежей не обязательны:
их логическое владение проверяется в коде. Redis, новая СУБД, Kubernetes и иные
инфраструктурные системы не добавляются без доказанного требования и отдельного scope.

### Обязательные условия комплекта

Версионные Dockerfile/Compose и документация запуска находятся в этом репозитории.
Пути конкретного implementation-пакета объявляются заранее; предполагаемая область
существующего плана — `ops/docker/dev/`, но её наличие этот документ не утверждает.

Основа образов и инструменты закреплены версией/digest; финальный запуск использует
проверенные digest, а не меняемый тег `latest`. Сборка включает исходный SHA и не
маскирует грязный checkout. Сборка и публикация образа не означают развёртывание.

Значения путей, адресов провайдеров, Host-policy и портов конфигурируются без
редактирования образа. В production нет Vite dev server, wildcard trusted-hosts
ради обхода ошибки, host profile, Docker socket, SSH agent или GitHub write-token.

Минимальные права и non-root обязательны там, где нет документированного препятствия;
записываемые пути перечислены явно. Проверить корректное завершение по сигналу.
Настоящие секреты не включать в layers, build arguments, Git, журналы и screenshots.
Для рабочего секрета нужны стабильный внешний источник, резервирование и процедура
восстановления; временный /tmp не считается постоянным хранилищем ключа шифрования.

Миграция исполняется одним назначенным процессом, повторный запуск безопасен.
Сервер не объявляется готовым до проверки конфигурации, схемы и доступности своих
данных. Жизнеспособность процесса, готовность API и здоровье обработчика различаются.
Restart-policy не заменяет recovery и не лечит автоматически все unhealthy-состояния.

## 4. Исполнители и сведения о проверке

**Три независимых уровня доказательств:**
1. Исходники и инструменты: статические/модульные проверки и точный diff.
2. Изолированная сборка: реальные контейнеры/браузер/API с временными данными и имитаторами.
3. Целевая эксплуатация: согласованный сервер, реальные внешние подключения и рабочий релиз.

Успех одного уровня не приписывается следующему. Хостовые особенности не имитируются
отчётом CI. Сломанный канал удалённого доступа не отменяет уровни 1–2, если существует
доступный независимый исполнитель.

Для каждого прогона сохранить JSON-отчёт и короткий русский итог. Обязательные поля:
репозиторий; source/base/checkout SHA; workflow/run/attempt; среда и версии инструментов;
Compose-project; source/config digest; image digest по сервисам; время начала/окончания;
контейнеры/тома/порты; идентификаторы испытаний и фактические outcomes; путь артефактов;
ограничения имитации; замечания; результат собственной очистки.

Статусы: PASS, FAIL, BLOCKED, NOT_RUN, NOT_APPLICABLE. Последний требует основания.
Отсутствие файла отчёта, сбой выгрузки или неразобранный формат не считаются PASS.
Число проверенных сценариев берётся из результатов, не из длины массива в карте.

Для воспроизводимых фикстур выполнить три независимых запуска с новыми данными.
Каждый должен пройти без скрытого повторного запуска упавшего теста. Повтор после
исправления — новый attempt с сохранённым первоначальным провалом.

Предлагаемые пределы только для CPU-фикстур: готовность стека 180 секунд, тестовое
задание 60 секунд. Изменение пределов требует заранее записанной причины; это не
утверждение production-производительности и не норматив для настоящей модели.

## 5. Обязательные испытания

| Идентификатор | Действие | Требуемый наблюдаемый результат |
|---|---|---|
| Д0-01 | Выполнить ограниченное задание на независимом GitHub-исполнителе | Подтверждены ОС, инструменты, сеть к нужным реестрам и exact checkout; не требуется D2 |
| Д0-02 | Сохранить свежие отчёты dependency/secret проверки и границы среды | Сырые данные, время и SHA сохранены; ошибки сети отличимы от находок; рабочие секреты/данные отсутствуют |
| Д1-01 | Собрать из чистого checkout | Репозиторий/версия совпадают; Dockerfile/Compose из Git; нет ручного копирования кода и чужих образов |
| Д1-02 | Запустить только свои контейнеры и открыть сайт | Веб и API одной сборки; готовность реальна; порты и Compose-группа записаны |
| Д1-03 | Создать двух тестовых пользователей, войти и выйти | Сессии выдаются/отзываются штатно; есть отрицательные проверки неверных данных и запрещённого доступа |
| Д1-04 | Создать изображение через UI/API и имитатор провайдера | Используется настоящая цепочка job/queue/result; задание завершается; объект, файл и учёт токенов согласованы |
| Д1-05 | Открыть результат, отметить избранное и использовать как исходник | Галерея читает реальную сохранённую запись; изменённое состояние перечитывается через API |
| Д1-06 | Опубликовать допустимый результат, открыть ленту гостем | Разрешённая публикация видна; приватный оригинал и объект другого пользователя не раскрываются; moderation не обходится |
| Д1-07 | Пересоздать свои контейнеры с теми же томами | Сохраняются пользователи, записи, избранное, публикация и контрольные суммы медиаданных; секретный источник стабилен |
| Д1-08 | Завершить отдельный тестовый прогон | Снимки браузера и журналы сохранены; удалены только временные ресурсы этого прогона; рабочие/чужие ресурсы не затронуты |
| Д2-01 | Завершить обработчик после захвата, затем запустить | Задание получает определённый исход по recovery; не остаётся навсегда running, не списывается повторно |
| Д2-02 | Повторить запрос и отмену с тем же ключом | Один финансовый эффект; допустимые повторы явно описаны; возврат не дублируется |
| Д2-03 | Запустить конкурентные потребители на одинаковом задании | Право обработки контролируется; чужая роль не запускает второй встроенный потребитель |
| Д2-04 | Получить согласованную копию БД/медиа и восстановить отдельно | SQLite integrity, migration ledger и DB↔media ссылки проходят; приложение читает восстановленный набор |
| Д2-05 | Подать повреждённую/неполную копию в отдельный restore-контур | Явный отказ/описанное неполное состояние; исходная копия и действующие данные не перезаписаны |
| Д2-06 | Сделать хранилище недоступным в изолированной среде | Readiness/ошибка отражают сбой; нет ложного успешного результата и бесконтрольного повторного списания |
| Д3-01 | Пройти матрицу включённых функций на тех же образах | Для каждого включённого сценария есть результат, конкретный тест и версия; gaps не скрыты за ссылкой на файл |
| Д3-02 | Проверить разрешённое соединение с реальной моделью | Установлены endpoint, сетевой путь, доступность и реальные результаты; имитатор не объявлен настоящей моделью |
| Д3-03 | Проверить CPU/RAM/диск/время на целевой конфигурации | Записаны нагрузка, наблюдения и утверждённые пределы; нет скрытого ресурсоёмкого воздействия на чужие службы |
| Д3-04 | Устранить/принять Windows- и factory-route ограничения | Озвучивание, опрос заданий и защищённые admin-функции имеют явное проверенное решение, не молча исключены |
| Д4-01 | Поднять теневую версию без рабочего трафика | Своё состояние и секреты; нет реальных писем/платежей/ботов; подтверждено соответствие поддерживаемых функций |
| Д4-02 | Отрепетировать откат на безопасных данных | Предыдущая версия читает совместимые данные либо выполнен безопасный согласованный restore; потери не скрыты |
| Д4-03 | После разрешения владельца перенести рабочую систему | Есть точный план, backup, остановка старой записи/потребителей, миграция и контрольный пользовательский путь |
| Д4-04 | Пройти согласованное наблюдение после переключения | Проверены публичный сайт, задания, медиа, здоровье и ошибки; выполнены критерии устойчивости и восстановления |

Для Д1-04 имитатор подменяет только внешнюю модель. Запись готового изображения
напрямую в БД, обход очереди, авторизации, списаний или gallery/feed логики запрещены.
Приёмочный тест не добавляет открытый служебный endpoint в production.

Д1-07 сравнивает значимые записи и файлы, не требует byte-identical SQLite-файла:
служебные записи и checkpoint могут законно изменить его байты.

Д2-01–Д2-03 выполняются на тестовом провайдере с регистрируемыми побочными эффектами.
При неопределённом результате внешнего вызова нельзя автоматически повторять платную
операцию. Нужны сверка по provider-id/idempotency key или явное состояние разбора.

## 6. Матрица поддерживаемых функций

Перед Д3 и Д4 фиксируется отдельная таблица фактической сборки. Для каждой функции:
включена/отключена/частична; UI и API; owner; способ испытания; результат; ограничение;
блокирует ли перенос; решение владельца при изменении доступности.

Обязательные строки: вход/сессии; Telegram/MAX; генерация и редактирование; задания;
галерея; публикация/лента; чат/history/tools; платежи/учёт; видео; распознавание речи;
озвучивание; административные модели/экономика; защищённые admin-операции; 3D.

3D не становится работающей функцией из-за существования контракта. Реальные платежи,
почта и сообщения никогда не выполняются без отдельного разрешения. Репозиторные
фикстуры провайдеров допускаются, но их результат не закрывает проверку live-сервиса.

Если маршрут есть в исходнике, но отсутствует в generated inventory, он отмечается
как неподтверждённый этой описью. До принятия соответствующей функции требуется
исправленный индекс либо отдельное воспроизводимое доказательство маршрута/прав.
Не подменять отсутствующую проверку пометкой «функция не нужна».

Известная гонка взаимного снятия прав администраторов остаётся явным замечанием до
исправления или ограниченного решения по риску. Зелёный sequential-тест не закрывает
конкурентный случай. Такие gaps нельзя обозначать как отсутствие ошибок продукта.

## 7. Сохранность, миграции и возврат

Резервирование выполняется существующим поддерживаемым механизмом; расширять его,
а не создавать вторую систему backup. Копия должна включать согласованное состояние
SQLite и медиа/индекс ссылок, версию схемы, время и проверяемые контрольные суммы.
Копирование одного живого .sqlite-файла при активном WAL не считается доказанным backup.

Восстановление сначала только в отдельные новые тома. Проверить integrity и ссылки,
потом открыть приложение. Нельзя включать реальные отправки из восстановленного outbox.

Перед Д4 согласовать допустимую потерю данных, время восстановления, рабочую нагрузку,
окно изменения и период наблюдения. Неразрешённые значения блокируют именно перенос,
а не сборку и безопасные испытания Д1. Обещание срока без репетиции недопустимо.

Старый и новый runtime не пишут одновременно в одну рабочую SQLite. При переключении
остановить старые consumers/listeners; webhook/polling ownership явно передать новому.
Миграции имеют журнал и проверенную совместимость. Откат образа не откатывает схему.
При отсутствии обратной совместимости нужен согласованный возврат данных или запрет
обновления до отдельного решения. Не восстанавливать молча поверх новых записей.

## 8. Безопасность и очистка

Стек и тесты не получают пользовательский профиль хоста, GitHub owner credential,
Docker socket, рабочие ключи, базы или media. Права build-runner на Docker не
передаются прикладному контейнеру. Публикация образов и PR — отдельные полномочия.

Имитаторы/фикстуры и временные секреты должны исключать случайный платный вызов:
тестовый конфиг плюс проверяемое ограничение сети/доступов, а не только обещание бота.
Логи ограничены по объёму, редактируются для удаления секретов до публикации артефакта.
Артефакты с персональными данными запрещены; сроки хранения задаются явно.

Запрещены глобальные prune/reset, удаление чужих volumes/networks, общий restart
Docker Desktop и широкая очистка host filesystem. Разрешена только очистка ресурсов,
чья принадлежность этому exact прогону доказана. Не удалять диагностические сведения
до их сохранения. Пропавший отчёт об очистке — отдельная незакрытая проверка.

Healthcheck только обнаруживает состояние. Для восстановления нужны restart/retry
policy, устойчивое состояние и тесты; внешний сбой модели не должен вызвать цикл
перезапуска всего приложения или израсходовать баланс повторными попытками.

## 9. Состав поставки и форма короткого задания

Поставка: версионный Compose/Dockerfile; инструкция запуска без ручной правки;
образцы конфигурации без секретов; источники образов и digest; тестовые фикстуры;
исполняемые проверки; отчёт, screenshots и журналы; ограничения; проверенная процедура
backup/restore/rollback со ссылками на существующие runbooks.

Задание исполнителю ссылается на репозиторий, текущую согласованную основу и
идентификаторы нужных испытаний. Оно не повторяет этот документ целиком.

Этот документ не фиксирует текущий PASS/FAIL рубежей, completed/active/next package
или состояние переходов. Единственный current router — `docs/NOW.md`; фактическое
прохождение критериев подтверждается evidence соответствующего Issue/PR/CI.
Ни один Docker acceptance criterion не считается пройденным самим наличием этого
канонического контракта.

Отчёт: результат рубежа; исходный SHA; PR и CI run; образы; пройденные/непройденные
