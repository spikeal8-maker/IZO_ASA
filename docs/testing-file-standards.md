# Ограничения и организация тестовых файлов IZO_ASA

Точка проверки: `tools/file_hygiene.py`. Действующие лимиты **строк исходного кода** определяет `architecture/contract.json` (`source_size_policy`), а не этот документ. Правила не заменяют проверку поведения продукта, `tools/verify.ps1`, тесты миграций или Docker acceptance.

## 1. Бюджет нового тестового файла

| Состояние | Строк | Размер UTF-8 | Решение |
|---|---:|---:|---|
| Обычный новый тест | до 500 | до 24 КиБ | Проходит контроль размера |
| Обоснованное исключение | до 750 | до 36 КиБ | Требуется конкретный `[[sizeReviews]]` в текущем Task Contract |
| Больше исключения | свыше 750 | свыше 36 КиБ | Разделить до объединения |
| Старый файл выше нормы | исторический | исторический | Не увеличивать ни строки, ни байты; сокращать постепенно |

Достаточно превысить **любой** из двух порогов, чтобы потребовалась проверка. Исключение разрешено только для нового/ранее компактного теста в границах 750 строк и 36 КиБ; старый большой тест не получает права расти из-за исключения. При переносе/переименовании старый файл сравнивается со своим настоящим Git-источником, чтобы обход через новое имя не работал.

Пример обоснования в `tasks/<PACKAGE>.toml`, когда оно действительно необходимо:

```toml
[[sizeReviews]]
path = "backend/test_example.py"
rationale = "Temporary isolated compatibility tests; split into targeted modules in the following package."
```

Не увеличивать лимиты `source_size_policy` в `architecture/contract.json` ради удобства. Стандарт 500/750 действует и для другого нового handwritten source; контроль размеров тестов добавляет к нему байтовые границы и **non-growth** для старых крупных файлов.

## 2. Как делить тесты

- Один файл — одна функция или ограниченный сценарий: `backend/test_<domain>_<behavior>.py`, `tools/test_<tool>.py`, `frontend/<feature>.test.ts`, `frontend/e2e-<scenario>.mjs`. Нельзя просто переименовать старый огромный файл и объявить декомпозицию.
- Переносить **группы проверок**, fixture и helper только с сохранением прежнего покрытия. Общий helper не должен содержать спрятанные assertion или новое бизнес-поведение.
- Изолированные временные SQLite/media/secrets и fake endpoints обязательны. Работающие сервисы, настоящие ключи, сообщения, деньги, GPU-вызовы и production не являются тестовыми данными.
- Тесты auth, billing, хранения, worker/recovery включают отрицательные сценарии, конкурентные гонки и проверки идемпотентности по требуемому risk class.
- Проверки frontend делятся на unit/component и браузерные E2E по конкретной странице; не смешивать десятки несвязанных пользовательских сценариев в одном E2E-скрипте.
- Тестовые отчёты, скриншоты и временные данные не попадают в исходные тесты и не используются как второй источник требований.

## 3. Автоматические проверки и объём действия

**Отдельная лёгкая проверка на GitHub-hosted Linux** (`.github/workflows/file-hygiene.yml`) без Docker, GPU, npm install, установленного сайта и вызовов внешних провайдеров:

1. Сравнивает точный `base SHA → head SHA` для добавленных, изменённых и переименованных тестов и Markdown.
2. Проверяет строки и UTF-8 байты; старые сверхлимитные файлы можно уменьшать, но не увеличивать.
3. Проверяет новые относительные ссылки в Markdown и ссылки, которые сломались из-за удаления или переноса файла.
4. Не меняет и не блокирует неизменённые старые файлы; `archive/**`, `docs/generated/**`, `docs/context/**` обслуживаются отдельными правилами. Корневой `README.md` считается навигатором, `TEST_PLAN.md` — рукописным документом; `AGENTS.md` имеет собственную политику.
5. Не утверждает, что продуктовые тесты прошли: контроль размеров и ссылок — **отдельный gate**, а полный/профильный CI остаётся обязательным по типу изменения.

Локально (с чистым checkout и известными SHA):

```bash
python -m unittest -v tools.test_file_hygiene
python -m tools.file_hygiene --base <BASE_40HEX> --head <HEAD_40HEX>
python -m tools.file_hygiene --inventory --head <HEAD_40HEX>
```

`--inventory` показывает старые превышения как долг, не объявляя их новыми ошибками. После безопасного разделения конкретного файла его новый бюджет становится обычным, без автоматического увеличения.
