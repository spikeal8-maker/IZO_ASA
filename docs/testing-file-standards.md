# Организация и ограничения тестовых файлов IZO_ASA

Строковые лимиты исходного кода — `architecture/contract.json` / `source_size_policy`.
Контроль файлов — `tools/file_hygiene.py`; локальных ссылок — его Markdown-модуль.
Это проверка структуры, не замена проверки поведения, полного CI или Docker-приёмки.

## Бюджет

| Файл | Обычный предел | Верхняя граница с review |
|---|---|---|
| Новый тест, conftest, текстовая fixture/helper | 500 строк и 24 КиБ UTF-8 | 750 строк и 36 КиБ, с валидным `sizeReviews` |
| Старый сверхлимитный файл | Прежний размер | Не растёт ни по строкам, ни по байтам |

Проверяются Python tests, `.test.*` / `.spec.*`, E2E/smoke/visual-скрипты,
`conftest.py`, код и текстовые данные в tests/fixtures/test_helpers.
Исполняемый анализатор `tools/test_health_audit.py` — не тест; его контролирует
исходная архитектурная политика. Бинарные fixtures не являются текстовым кодом.

Лимит срабатывает по любому измерению. Переименование учитывает предыдущий путь;
возврат из исключённого каталога не даёт исторического разрешения на большой файл.
Не повышать лимиты ради зелёного результата и не удалять assertions при разделении.

## Исключение — только через существующий Task Contract

`sizeReviews` читается тем же `parse_manifest`, что и обычные задания. Manifest
должен иметь текущую базу сравнения, единственный id и разрешать проверяемый путь.
Неполный TOML, старое задание или запись вне scope не считаются одобрением.
Полный формат: [task-contract-guide.md](task-contract-guide.md).
Исключение ограничивает размер; независимое review и остальные gates остаются обязательными.

## Организация

Один тестовый файл отвечает за ограниченное поведение. Общие fixtures/helpers
соседствуют с областью тестирования, а не скрывают большой тестовый монолит.
Сохранять идентичность сценариев и покрытие; сравнивать collection и результаты
до/после разделения. Скриншоты/отчёты — evidence, не исполняемая спецификация.

Изолированные временные SQLite/media/secrets и fake providers обязательны.
Запрещены production-данные, настоящие платежи, письма и GPU-вызовы в обычных тестах.
Auth/billing/storage/workers требуют отрицательных, race/idempotency и recovery
проверок по классу риска. UI требует отдельного desktop/mobile поведения.

## Запуск контрольного инструмента

Из чистого checkout с Python проекта. Установка parser касается только tooling:

```bash
python -m pip install --only-binary=:all: --require-hashes -r tools/file_hygiene_requirements.txt
BASE=$(git rev-parse origin/main)
HEAD=$(git rev-parse HEAD)
python -m tools.file_hygiene --base "$BASE" --head "$HEAD" --comparison merge-base
python -m tools.file_hygiene --inventory --head "$HEAD"
```

Для фактического push CI передаёт его `before/head` с режимом direct, для PR —
общую базу ветвления. Нельзя молча подменить отсутствующий commit другим.
Inventory показывает долг по размерам и ссылкам; отчёт не означает, что долг исправлен.

## CI и границы результата

Один вход — `.github/workflows/ci.yml`; он вызывает Linux reusable
`.github/workflows/file-hygiene.yml`. Лёгкие проверки используют Git-объекты,
временные test-repositories и hash-pinned parser, не Docker/рабочие сервисы.
После успешной классификации прикладной/неизвестный scope запускает прежний Windows
job; его существующие проверки сохранены. Перед ними устанавливается тот же
hash-pinned parser только в CI, иначе новые тесты не смогли бы собраться.
Portable CI/review, прикладной CI и контейнерная/production приёмка — разные доказательства.
`[skip ci]` не является выбором безопасного контура: оно пропускает автоматические проверки.
